# AGENTS.md

이 저장소에서 작업하는 모든 에이전트는 이 문서와 `개발했슈_위젯공유플랫폼_PRD.md`를 따라야 한다.

## 1. 제품 한 줄 정의

슈크림마을의 바이브코딩 동아리 **개발했슈** 멤버들이 만든 무료 노션 위젯을 소개하고, 방문자가 직접 사용한 뒤 임베드 링크를 복사할 수 있는 공개 위젯 공유 플랫폼이다.

서비스명은 아직 미정이다. 코드와 문서에서 임시로 `개발했슈 위젯 제빵소` 또는 `위젯 제빵소`를 사용할 수 있지만, 이름을 여러 파일에 하드코딩하지 말고 한곳에서 교체할 수 있게 관리한다.

## 2. 제품 요구사항의 우선순위

충돌 시 다음 순서로 판단한다.

1. 사용자의 최신 명시적 요청
2. 이 `AGENTS.md`
3. `개발했슈_위젯공유플랫폼_PRD.md`
4. 기존 구현과 샘플 콘텐츠

PRD에 없는 기능을 “있으면 좋을 것 같다”는 이유로 추가하지 않는다. 범위를 넓혀야 한다면 구현 전에 사용자에게 확인한다.

## 3. 현재 확정된 제품 범위

반드시 포함한다.

- 반응형 사이드바와 모바일 내비게이션
- 홈 화면과 상단 소식 배너
- 위젯 목록, 검색, 카테고리 필터
- 위젯 상세 정보와 실제 위젯 미리보기
- 임베드 링크 복사
- Google 로그인
- 일반 사용자, 제작자, 관리자 권한
- 기수별 가입 코드 인증과 제작자 자동 승인
- 한 사용자의 복수 활동 기수 등록
- 로그인 사용자의 관심 위젯
- 제작자 목록, 제작자 상세, 개인 프로필
- 제작자의 위젯 등록·수정과 프로필 자동 연동
- 개발했슈 및 제빵사 소개
- 기본 SEO 및 AEO
- 이용약관과 개인정보처리방침 진입점

현재 범위에서 제외한다.

- 결제, 유료 플랜, 구독, 환불
- 댓글, 후기, 팔로우, 알림, 커뮤니티 게시판
- 외부 일반 사용자의 위젯 등록
- 조회수·복사수 공개 표시
- 인기순 랭킹
- SNS 공유 버튼
- 플랫폼 공통 위젯 커스터마이저
- 다국어
- 복잡한 운영 통계 대시보드

제외 기능을 위한 빈 UI, 사용 불가능한 버튼, 미래용 추상화도 만들지 않는다.

## 4. 핵심 사용자 흐름

### 방문자

`위젯 구경하기 → 상세 정보 확인 → 실시간 사용 → 임베드 링크 복사 → 노션에 붙여넣기`

- 이 흐름에는 로그인이 필요 없어야 한다.
- 위젯 사용을 결제나 회원가입으로 막지 않는다.
- 상세 페이지에서 링크 복사 버튼을 가장 명확한 행동으로 제공한다.

### 제작자

`Google 로그인 → 활동 기수 선택 → 가입 코드 검증 → 제작자 권한 부여 → 프로필 작성 → 위젯 등록 → 프로필에 자동 노출`

### 다기수 활동자

- 기존 계정에서 `활동 기수 추가`를 제공한다.
- 새 기수를 추가할 때 해당 기수의 가입 코드를 다시 검증한다.
- 동일 사용자가 동일 기수를 중복 등록하지 못하게 한다.

## 5. 권한 규칙

| 기능 | 일반 사용자 | 제작자 | 관리자 |
|---|---:|---:|---:|
| 공개 위젯 열람·복사 | 가능 | 가능 | 가능 |
| 관심 위젯 저장 | 가능 | 가능 | 가능 |
| 개인 프로필 수정 | 가능 | 가능 | 가능 |
| 활동 기수 인증 | 가능 | 가능 | 가능 |
| 위젯 등록 | 불가 | 가능 | 가능 |
| 본인 위젯 수정 | 불가 | 가능 | 가능 |
| 다른 제작자 위젯 관리 | 불가 | 불가 | 가능 |
| 기수 코드·사용자 권한 관리 | 불가 | 불가 | 가능 |

- 권한은 서버에서 확인한다. 클라이언트 UI를 숨기는 것만으로 권한을 구현하지 않는다.
- 클라이언트에서 전달한 사용자 ID, 이메일, 역할을 신뢰하지 않는다.
- 제작자는 자신이 소유한 위젯만 수정할 수 있다.

## 6. 인증 및 보안

- 최종 인증 방식은 Google OAuth다.
- 실제 OAuth Client ID가 없는 개발 환경에서는 데모 상태임을 명시하고 실제 로그인처럼 오해시키지 않는다.
- 운영 배포에서 가짜 로그인, 임의 사용자 전환, 하드코딩된 관리자 권한을 남기지 않는다.
- 기수별 가입 코드는 평문으로 저장하거나 클라이언트 번들에 포함하지 않는다. 서버에서 해시를 비교한다.
- 입력 URL은 `https://`만 허용한다. `javascript:`, 로컬 주소, 위험한 스킴을 차단한다.
- 업로드는 확장자만 보지 말고 MIME 타입과 용량을 검증한다.
- 사용자 입력 출력 시 XSS를 방지한다.
- 위젯 iframe에는 기능에 필요한 최소 sandbox 및 permissions 정책을 적용한다.
- 인증 키, OAuth secret, 가입 코드, 저장소 토큰을 커밋하지 않는다.

## 7. 위젯 등록 요구사항

등록 UI는 단계형으로 유지한다.

### 1단계: 기본 정보

- 위젯 이름: 필수
- 한 줄 설명: 필수, 권장 80자 이내
- 상세 설명: 필수
- 카테고리: 필수, 단일 선택
- 제작자의 한마디: 선택

### 2단계: 위젯 연결

- 배포 링크: 필수
- 임베드 링크: 필수
- 배포 링크와 임베드 링크 동일 여부
- 모바일 지원 여부
- 로그인 필요 여부
- 외부 API 사용 여부

### 3단계: 이미지와 가이드

- 대표 이미지: 필수
- 추가 이미지: 선택
- 사용 가이드: 선택
- 외부 가이드 링크: 선택

대표 이미지는 PNG, JPG, WebP만 허용한다. 권장 크기는 1200×750px 이상, 최대 용량은 5MB다.

### 4단계: 미리보기와 제출

- 실제 공개 화면과 유사한 최종 미리보기를 제공한다.
- 제출 직후 상태는 `pending`이다.
- 관리자가 승인하면 `published`로 변경한다.

허용 상태는 `draft`, `pending`, `published`, `hidden`이다.

## 8. 정보와 데이터 모델

핵심 엔터티는 다음과 같다.

- `users`: Google 사용자, 프로필, 역할
- `cohorts`: 개발했슈 기수와 가입 코드 해시
- `user_cohorts`: 사용자와 복수 활동 기수 관계
- `categories`: 위젯 카테고리
- `widgets`: 위젯 정보, 링크, 가이드, 공개 상태
- `favorites`: 사용자와 관심 위젯 관계

필수 관계와 제약:

- `user_cohorts(user_id, cohort_id)`는 유일하다.
- `favorites(user_id, widget_id)`는 유일하다.
- 모든 위젯은 대표 제작자 한 명과 연결된다.
- 제작자 페이지에는 `published` 위젯만 공개한다.
- 현재는 공동 제작자를 구현하지 않는다.
- 내구성 있는 사용자·위젯·관심 데이터는 브라우저 저장소가 아니라 서버 데이터베이스에 저장한다.
- `localStorage`는 테마, 닫은 배너처럼 기기 한정 UI 환경설정에만 사용한다.

상세 필드 정의는 PRD의 데이터 모델을 따른다.

## 9. 콘텐츠와 브랜드

핵심 가치는 `재미 · 공유 · 성장`이다.

- 위젯은 상품이 아니라 멤버가 직접 구운 성장 결과물로 소개한다.
- 귀여운 표현은 사용하되 기능 의미를 흐리지 않는다.
- 브랜드 문구와 일반 기능명을 함께 쓴다. 예: `노션에 담기 · 링크 복사`.
- 캐릭터는 히어로, 로그인, 빈 화면, 성공·오류 상태에 집중한다.
- 위젯 카드와 미리보기가 장식보다 먼저 보여야 한다.
- 기존 슈크림마을 공식 캐릭터와 로고는 사용 권한이 확인된 원본만 사용한다.
- 로고가 제공되기 전에는 교체 가능한 텍스트 로고나 CSS 형태를 사용한다.
- 임의로 공식 캐릭터처럼 보이는 신규 자산을 만들지 않는다.

권장 브랜드 문장:

> [서비스명]은 노션 커뮤니티 슈크림마을의 바이브코딩 동아리 ‘개발했슈’가 운영하는 무료 노션 위젯 공유 플랫폼입니다.

### 컬러 토큰

- Forest Green `#285C3A`: 브랜드 및 주요 버튼
- Custard Cream `#FFF2C7`: 강조 배경
- Bakery Beige `#F7F1E8`: 전체 배경
- Toast Brown `#8B5E3C`: 제목과 선
- Strawberry Pink `#F6A9B8`: 관심 위젯과 포인트

색상값을 컴포넌트마다 반복하지 말고 디자인 토큰으로 관리한다.

## 10. UI 및 접근성

- 데스크톱은 사이드바, 모바일은 햄버거 또는 모바일 내비게이션을 사용한다.
- 카드 모서리는 18~24px, 얇은 베이지·브라운 테두리를 기본으로 한다.
- 주요 버튼의 의미와 현재 상태가 명확해야 한다.
- 모든 상호작용 요소는 키보드로 접근 가능해야 한다.
- 모바일 터치 영역은 최소 44×44px로 한다.
- 색상만으로 상태를 구분하지 않는다.
- 이미지에는 내용에 맞는 `alt`를 제공한다. 장식 이미지는 빈 `alt`를 사용한다.
- 모달은 포커스 이동, 포커스 가두기, ESC 닫기, 닫힌 후 원래 요소로 포커스 복귀를 지원한다.
- 로딩, 빈 화면, 오류, 복사 성공에 텍스트 피드백을 제공한다.
- 애니메이션은 짧고 절제해서 사용하며 `prefers-reduced-motion`을 존중한다.

## 11. SEO 및 AEO

각 위젯 상세 페이지는 다음 질문에 HTML 텍스트로 답해야 한다.

- 이 위젯은 무엇인가?
- 누구에게 필요한가?
- 어떤 문제를 해결하는가?
- 무료인가?
- 로그인이 필요한가?
- 모바일에서 작동하는가?
- 어떻게 설치하는가?
- 외부 데이터를 사용하는가?
- 제작자는 누구인가?
- 마지막 업데이트는 언제인가?

필수 기술 사항:

- 위젯과 제작자별 고유하고 크롤링 가능한 URL
- 페이지별 고유 title과 description
- canonical URL
- XML sitemap과 실제 변경일 기반 `lastmod`
- robots.txt
- Open Graph 메타데이터
- 중복 또는 검색어만 바꾼 얇은 페이지 금지
- iframe이나 이미지 안의 내용만으로 핵심 정보를 전달하지 않기

구조화 데이터:

- 사이트: `WebSite`
- 운영 주체: `Organization`
- 위젯: `WebApplication` 또는 `SoftwareApplication`
- 제작자: `Person`
- 탐색 경로: `BreadcrumbList`

구조화 데이터는 화면에 보이는 사실과 일치해야 한다. 무료 위젯의 `offers.price`는 `0`으로 표현한다.

## 12. 저장소와 구현 규칙

### 현재 파일 역할

- `개발했슈_위젯공유플랫폼_PRD.md`: 제품 요구사항의 상세 원본
- `app/`: React/Vinext 기반 제품 구현
- `static/`: 의존성 없이 확인 가능한 정적 프로토타입
- `dist/`: 배포 빌드 결과물. 직접 기능 개발을 하지 않는다.
- ``: 사용자에게 전달하는 문서와 패키지. 제품 소스의 기준으로 사용하지 않는다.
- `.openai/hosting.json`: Sites 프로젝트 및 리소스 바인딩

### 소스 기준

- 신규 제품 기능은 `app/`을 기준으로 구현한다.
- `static/`을 계속 제공해야 하는 경우 동일한 사용자 흐름을 유지하되, 두 구현이 조용히 달라지지 않도록 변경 내용을 명시한다.
- `dist/`와 ZIP 파일은 소스 변경 후 다시 생성한다. 생성물만 직접 수정하지 않는다.
- 실제 로고, 위젯, 제작자 데이터가 제공되기 전에는 샘플임을 코드와 UI에서 구분 가능하게 유지한다.

### 환경과 배포

- 이 프로젝트에는 `.openai/hosting.json`이 있으므로 Sites 관련 작업에는 Sites 빌드·호스팅 지침을 따른다.
- 서비스 키와 OAuth 설정은 환경 변수 또는 호스팅 런타임 설정으로 관리한다.
- `.env.example`에는 키 이름과 설명만 기록하고 실제 값을 넣지 않는다.
- 데이터베이스 스키마 변경에는 마이그레이션을 포함한다.
- 배포 전에 현재 소스 상태로 새 빌드를 생성하고 검증한다.

## 13. 변경 작업 절차

1. 작업 전에 이 문서와 관련 PRD 섹션을 읽는다.
2. 기존 변경과 파일 상태를 확인하고 사용자 작업을 덮어쓰지 않는다.
3. 요청 범위를 벗어나지 않는 가장 작은 완전한 변경을 설계한다.
4. 인증·권한·데이터 변경은 클라이언트와 서버 경계를 먼저 정의한다.
5. 기능 구현 후 데스크톱과 모바일 핵심 흐름을 검증한다.
6. SEO/AEO에 영향을 주는 화면은 메타데이터와 구조화 데이터도 함께 확인한다.
7. 테스트와 빌드를 실행하고 실제 실패를 수정한다.
8. 변경한 기능, 검증 결과, 남은 외부 설정을 사용자에게 알린다.

중요한 서비스명, 실제 브랜드 자산, 인증 제공자 설정, 데이터 삭제 정책처럼 결과를 크게 바꾸는 정보가 없으면 구현 전에 사용자에게 확인한다. 단순한 샘플 문구나 되돌릴 수 있는 UI 세부사항은 합리적으로 가정하고 진행한다.

## 14. 최소 검증 항목

기능 변경 시 관련 항목을 검증한다.

- 비회원이 위젯 목록과 상세를 볼 수 있는가
- 비회원이 임베드 링크를 복사할 수 있는가
- 비회원이 관심 위젯을 누르면 로그인이 안내되는가
- 일반 사용자가 위젯 등록 API를 호출할 수 없는가
- 올바른 기수 코드만 제작자 권한을 부여하는가
- 동일 기수를 중복 등록할 수 없는가
- 제작자가 자신의 위젯만 수정할 수 있는가
- 등록한 위젯이 해당 제작자 프로필에 연결되는가
- `pending` 위젯이 공개 목록에 노출되지 않는가
- 관리자가 위젯 상태를 변경할 수 있는가
- 잘못된 URL과 위험한 업로드가 거부되는가
- 복사 성공과 오류 상태가 사용자에게 전달되는가
- 검색과 카테고리 필터를 함께 사용할 수 있는가
- 모바일에서 내비게이션, 상세, 등록 폼을 사용할 수 있는가
- 키보드로 핵심 흐름을 완료할 수 있는가
- 위젯 상세의 텍스트와 구조화 데이터가 일치하는가
- 결제 또는 유료 플랜으로 오해할 UI가 없는가

## 15. 출시를 막는 조건

다음 중 하나라도 해당하면 운영용 출시 완료로 보고하지 않는다.

- Google 로그인이 데모 또는 가짜 로그인 상태
- 역할 검증이 클라이언트에만 존재
- 기수 코드가 평문 또는 클라이언트 코드에 포함됨
- 제작자가 다른 사용자의 위젯을 수정할 수 있음
- 등록·관심 위젯 데이터가 새로고침 후 사라짐
- 위젯 임베드 링크가 노션에서 동작하지 않음
- 이용약관 또는 개인정보처리방침이 없음
- 실제 콘텐츠 대신 샘플 위젯·샘플 제작자가 공개됨
- 로고나 캐릭터의 사용 권한이 확인되지 않음
- 모바일 핵심 흐름이 깨짐
- OAuth secret, 가입 코드, 토큰이 저장소에 포함됨

외부 키나 실제 콘텐츠가 없어 위 조건을 해소할 수 없다면, 구현 가능한 범위를 완료한 뒤 남은 항목을 명확한 배포 차단 요소로 보고한다.
